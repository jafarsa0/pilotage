Pilotage lets an MCP server publish the checkable competence required to use its complex tools, so any compatible agent can learn, validate, plan, execute, and trace them through a common interface: whole programs, against live systems, with the result on the record.

Why it exists

Wherever agents meet sophisticated systems (a SQL engine, an automation platform, a workflow processor), the same three problems repeat.

PROBLEM 1

Schemas describe structure, not languages

A JSON Schema can say a field is a string. It cannot teach the grammar the string must be written in, the names it may reference, or the rules that make it meaningful. The hard part of the input is exactly the part the schema cannot see.

PROBLEM 2

Complex work rarely succeeds in one call

Real programs are drafted, checked, repaired, and only then run. A bare tool call gives an agent one confident shot and an opaque failure. There is no standard way to validate first, see the blast radius, or prove what actually happened.

PROBLEM 3

Competence does not scale when hardcoded

Today each agent bakes in private knowledge of each system it drives. That knowledge dies with the integration. Publishing competence on the server (checkable, versioned, discoverable) makes it work once, for every agent.

The contract

Pilotage standardizes the loop, not the language. Any program language a server speaks (SQL dialects, rule DSLs, workflow JSON) gets the same verifiable envelope, expressed entirely with MCP's own primitives.

Closed diagnostic codes

Validation failures come from an enumerated set the server publishes, each with a machine-readable path into your program, repairable in one step, not guessable from prose.

Risk in the plan, gated by the Host

Before execution, the plan aggregates per-step risk up to max_risk. Destructive plans are approved by a human outside the model; the record decides what needs a signature.

Drift refusals

Pin a run to the catalog_version you validated against. If the world moved in between, the server refuses before anything executes: staleness is a value, not a surprise.

Decisions on the record

Traces record which branch ran and why, per iteration. “It succeeded but did nothing” stops being a mystery: the untaken arm is checkably absent.

Failure is a value

Invalid programs, drifted catalogs, and half-completed runs return as statuses with evidence: never crashes, never transport errors, never retry-bait.

Exactly-once, on request

Idempotency keys make retries safe: identical requests replay the recorded response, and reusing a key with a different payload is a loud, typed conflict.

See it catch the classic mistake

Live output from Harborview, the public example server, a simulated smart building speaking buildingflow/1, a language invented for it, which no model has ever seen in training. These exact request/response pairs are replayed against the server in CI.

request → validate_flow
{
  "flow": { "steps": [ {
    "id": "on",
    "do": "call",
    "device": "light.loby",   ← typo
    "action": "turn_on"
  } ] }
}
response · live, replayed in CI
{
  "valid": false,
  "diagnostics": [ {
    "severity": "error",
    "code": "unknown_device",   ← closed set
    "path": "/steps/0/device",  ← exact member
    "message": "unknown device 'light.loby'",
    "hint": "close match: light.lobby"
  } ],
  "catalog_version": "cv_590fefad56a7a504"
}

Not a stack trace, not a guess: a closed code, a path, a hint. An agent repairs this deterministically and re-validates, then runs with the catalog token pinned. Walk the whole loop in the first guide, and the failure modes in the second.
